## Why

在模糊關閉（前端預設）的正式情境下，16K 機型（15120×6230，每層畫布 9420 萬像素）一趟切片的時間約有三分之二花在「畫每一層圖」，而這段時間幾乎都是在掃描空白。以同型 CPU（i7-11370H）的既有量測為例：總耗時 43.49 秒中 Rasterizing 佔 28.96 秒（66.6%），其中核心光柵化約 20 秒、預覽產生約 9 秒；但畫布逾九成為全黑（第 316 層點亮 8.49%，第 60 層 0.90%）。

原因是每一層都會對整張畫布做四次與繪製面積無關的全幅面掃描：

1. `AGGRaster::reset()` 清空整張緩衝。
2. SL1 的 AA 灰階量化讀過整張緩衝（雖有 8 位元組全黑／全白跳過，仍須讀取）。
3. `RLERasterEncoder` 逐位元組走訪每個像素，沒有任何跳過。
4. `PNGPreviewEncoder` 的區塊平均逐像素累加，沒有任何跳過。

前一個變更 `optimize-slice-performance` 已移除可證實的無用功（blur 閘控、支撐去重、raster 執行緒重用等），並在結論中明確指出剩餘成本「由掃描整張畫布主導」，dirty-tile 稀疏化是唯一吃得到這九成空白的手段。本次探索另外確認了三項前提：

- **模糊確實完全關閉。** 前端送出 `Image Blur = false`，後端 `gate_blur` 將 `blur` 歸零並寫入 `config.ini`，引擎的 `blur_config > 0` 分支不會執行；切片流程不呼叫 `PUT /config`，因此不存在繞過閘控的路徑。
- **抗鋸齒本身不是瓶頸。** AGG 以面積覆蓋率計算邊緣灰階，並非超取樣；2x/4x/8x 只改變量化階數，成本相同。
- **其他段落收益小。** STL 上傳走本機迴路、一人使用時排隊時間通常為零、結果下載約 1 秒；前端支撐網格 5 倍重複的根因已修復。

因此本變更只處理畫布掃描這一個瓶頸。另外，前次的驗收基準 job（`b1d3a041`）與逐層 SHA-256 比對腳本皆已遺失，必須先重建基準，才能驗證「輸出不變」與「確實變快」。

## What Changes

- **重建效能與正確性基準（不改產品行為）**
  - 建立可重現的測試案例：以 `fixture-surgical-guide-18-19.stl`（封閉單一零件、125,602 面、高 24.6 mm）排版作為標準案例，並固定一份預先產生的 `support.stl`，每次以 `--import-support-stl` 匯入，避免支撐產生的不確定性污染比較。
  - 建立邊際案例：單顆小牙冠（佔平台約 0.2%）、滿版平板（約佔平台 88%）。
  - 將「解壓後每層層檔與每張預覽圖的 SHA-256 比對」固化為 repo 內的工具，不再只存在暫存目錄。
- **第 1 步：編碼器跳過整段同色區段**
  - `RLERasterEncoder` 與 `PNGPreviewEncoder` 以 8 位元組為單位判斷整段是否同色（涵蓋全黑與全白），整段同色時直接累加，不逐位元組走訪。
  - 屬純效能改動，輸出逐位元組不變。
- **第 2 步：dirty-tile 格子化**
  - raster 在「實際寫入像素」處記錄被寫過的格子，模型軌（AA 繪製）與支撐軌（`draw_binary()`）皆須記錄，不以多邊形外框推估。
  - `reset()` 改為只清除上一層寫過的格子；AA 灰階量化、RLE 編碼、預覽降取樣改為只處理被寫過的格子，全黑格子直接以算術產生結果。
  - 格子邊長取 40 的倍數，使其同時對齊 8 位元組區段與所有預覽縮放分母（4、5、8、10）；幅面邊緣不整除時的不完整格子須正確處理。
  - RLE 同色段會跨行延續，跳過黑色格子時黑色長度須跨行累加，產出才能與原實作一致。
  - 屬純效能改動，輸出逐位元組不變。
- **各掃描階段的耗時量測**：為清除、繪製、AA 量化、RLE 編碼、預覽產生分別加入計時輸出，補上前次缺少的細項數據。
- **不做的事**
  - 不處理模糊路徑（前端預設關閉；前次變更已完成分帶重寫）。
  - 不處理 STL 上傳、排隊調度、結果下載等非關鍵傳輸段。
  - 不處理引擎前半段（網格載入、修補、切層、支撐）。
  - 不做 bbox 級畫布裁切（零件散佈於平台，收益上限低）。
  - 不保證跨平台（Windows 與 macOS 之間）輸出位元一致。

## Capabilities

### New Capabilities

- `raster-performance-baseline`：定義光柵化效能改動的可重現基準與驗收流程——標準案例與邊際案例的組成、固定的切片參數與支撐網格、量測指標與取樣次數、逐層（含預覽圖）SHA-256 比對工具的輸入輸出，以及「只在同一平台比較改動前後」的比對規則。

### Modified Capabilities

- `sla-raster-performance`：
  - 「純效能改動不得改變任何層檔位元」的涵蓋範圍擴充至同色跳過與 dirty-tile，且驗收對象由層檔擴及預覽圖，並須在不同執行緒數（`--threads 1`、`2`、`8`）與重複執行下皆成立。
  - 「重用的 raster 在每層使用前須完全清除」改為「須清除上一層所有被寫入的區域」：原 requirement 已預留「能精確追蹤寫入區域之前才須清除整張」的前提，本變更即為滿足該前提的實作。
- `slice-preview-export`：「預覽降取樣採區塊平均，並提供整數倍快路徑」新增同色區塊與未寫入格子的跳過路徑，其輸出 SHALL 與通用路徑逐位元組相同。

## Impact

**驗收基準**

| 項目 | 主基準 | 次基準 |
| --- | --- | --- |
| 機型 | Sonic Mighty Revo 16K（15120×6230，平台 211.68×118.37 mm） | Sonic Mini 8K S（7536×3240，平台 165.79×71.28 mm） |
| 排版 | 導板 8 顆（4×2），外框總和約佔平台 67% | 導板 3 顆（3×1），外框總和約佔平台 53% |
| 層數 | 約 590 層（推算：抬高 5 mm + 模型 24.6 mm，未實跑） | 同左 |

- 共同參數：層厚 0.05 mm、`anti_aliasing = 1`、`anti_aliasing_level = 1`（UI 4x 預設）、`gray_level = 1`（前端預設）、`blur = 0`、`gamma_correction = 1.0`、`SLA_LAYER_RLE=1`、預覽縮放比依 `preview_scale_for()`。
- 量測環境：i7-11370H（4C/8T）、16 GB、Windows 11，與前次量測同型 CPU。每組執行 3 次取中位數。
- 改動前、改動後的引擎 SHALL 由同一份原始碼基底與同一套編譯設定自行建置。

**驗收條件**

1. 解壓後每一層層檔與每一張預覽圖的 SHA-256 與改動前 100% 一致，在 `--threads 1`、`2`、`8` 與重複執行下皆成立。
2. 主基準的「畫每一層圖」階段耗時至少減少 50%。
3. 峰值記憶體不得增加。
4. 滿版平板案例的耗時不得比改動前慢超過 3%。

**受影響的程式碼**

- `third_party/prusaslicer_fork`（submodule，需獨立 commit 並更新父 repo 指標）：
  - `src/libslic3r/SLA/RasterBase.cpp`、`RasterBase.hpp`：`RLERasterEncoder`、`PNGPreviewEncoder`。
  - `src/libslic3r/SLA/AGGRaster.hpp`：寫入格子記錄、`reset()`、`encode()`。
  - `src/libslic3r/Format/SL1.cpp`：AA 灰階量化後處理。
  - `src/libslic3r/Format/SLAArchiveWriter.hpp`、`SLAArchiveWriter.cpp`：`draw_layers()` 與各階段計時。
  - `tests/sla_print`：編碼器與 dirty-tile 的單元測試（全黑、全白、角落單點、跨行長同色段、同色段長度格式邊界 16／4096／1048576、不完整邊緣格子）。
- 本 repo：新增基準案例的產生方式與逐層 SHA-256 比對工具（位置與測試資料的入庫方式於 design 決定）。
- `agent/` 的 Python 程式、CLI 參數與 API：不變。
- DS-Online 前端：不受影響。

**風險與待確認事項**

- dirty-tile 讓同一條執行緒的 raster「記得上一層寫過哪裡」，漏記任何一格都會輸出錯誤像素，且可能只在特定執行緒排程下出現；因此以多種執行緒數與重複執行的逐層比對作為必要驗收。
- 標準案例的原始 STL 位於 repo 外（`D:\tool\stl\phrozen\tooth`），是否可入庫或只記錄其 SHA-256 與產生步驟，於 design 決定。
- 目前打包版引擎的 build 日期與 fork 指標 `5bc83b08f` 同日，但未驗證兩者確實對應，故不得以打包版作為改動前的基準。
