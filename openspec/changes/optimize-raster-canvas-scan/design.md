## Context

動機與驗收條件見 [proposal.md](proposal.md)。本文件只處理「怎麼做」。

### 現行每層流程

光柵化由 [SLAPrintSteps.cpp:1686-1715](../../../third_party/prusaslicer_fork/src/libslic3r/SLAPrintSteps.cpp#L1686-L1715) 的 `lvlfn` 與 [SLAArchiveWriter.hpp:97-109](../../../third_party/prusaslicer_fork/src/libslic3r/Format/SLAArchiveWriter.hpp#L97-L109) 的 `draw_layers()` 組成。每一層在一條 TBB 執行緒上依序執行：

```
ThreadBoundRasters::acquire()
  └─ reset()                    ① 全幅面寫入（clear 整張緩衝）
lvlfn
  ├─ draw(model polygons)          AGG 掃描線，只寫入被覆蓋的像素
  ├─ apply_postprocess()        ② 全幅面讀取（SL1 AA 量化，8 位元組全 0/全 FF 跳過）
  └─ draw_binary(support)          AGG 掃描線（門檻 gamma）
encode(RLERasterEncoder)        ③ 全幅面逐位元組讀取
encode(PNGPreviewEncoder)       ④ 全幅面讀取（區塊平均，逐像素累加）
```

①～④ 的成本只與幅面大小有關，與畫了多少東西無關。16K 幅面每層 94,197,600 位元組，而點亮比例通常低於一成。

### 既有約束（必須維持）

- **raster 與執行緒綁定**：`ThreadBoundRasters` 以 `tbb::enumerable_thread_specific` 保證一個 raster 只被一條執行緒使用（spec `sla-raster-performance`）。本設計新增的狀態全部掛在 raster 實例上，因此自動繼承這個保證。
- **`reset()` 為純虛擬**：忘了清除累積狀態會變成編譯錯誤，而不是靜默的錯誤輸出（[RasterBase.hpp:119-129](../../../third_party/prusaslicer_fork/src/libslic3r/SLA/RasterBase.hpp#L119-L129)）。本設計沿用同一個原則：寧可編譯失敗，也不要靜默出錯。
- **`reset()` 現行註解**明確寫著：只清除上一層寫過的區域，前提是所有消費端對「哪個區域」有一致認知（[AGGRaster.hpp:218-223](../../../third_party/prusaslicer_fork/src/libslic3r/SLA/AGGRaster.hpp#L218-L223)）。本設計的格子表就是這個唯一的共同認知。
- **RLE 格式須與 `agent/prz_encoder.py:_rle_encode_layer` 逐位元組一致**，後端直接拿來組 PRZ。
- **預覽縮放分母只會是 4、5、8、10**（[preview_scale.py:33](../../../agent/preview_scale.py#L33)），且全部走整數倍快路徑。
- **fork 以 C++17 建置**（`CMAKE_CXX_STANDARD 17`），不能使用 `std::countr_zero`。
- **其他使用者**：`AnycubicSLA` 的編碼器、GUI 字型預覽工作、`RasterToPolygons`（`read_pixel`）、`test_marchingsquares` 都直接讀取完整緩衝。它們不在本次優化範圍內，但不得被改壞。

## Goals / Non-Goals

**Goals:**

- 讓 ①～④ 的成本隨「實際寫入的面積」變化，而不是隨幅面大小變化。
- 所有改動維持逐位元組相同的層檔與預覽圖，並能在同一支 binary 內切回原演算法做對照。
- 為「漏記寫入區域」這類只在特定排程下出現的錯誤，提供結構性的防護與可重複的偵測手段。
- 重建一套不含病患資料、可在不同機器重現的基準與比對工具。

**Non-Goals:**

- 不加速 blur 路徑。`blur > 0` 時回到全幅面後處理（見 D5）。
- 不使用 SSE2／AVX2／NEON 等平台專屬指令集；第 1 步只用可攜的 64 位元字組運算（SWAR）。
- 不改 `RasterEncoder`、`RasterPostProcessor` 既有簽章的語意，不影響 `AnycubicSLA` 與 GUI 使用端。
- 不改 agent 的 CLI 參數、API 與 Python 程式。
- 不保證 Windows 與 macOS 之間輸出位元一致。

## Decisions

### D1：正確性論證的核心——RLE 輸出只由「最大同色段分解」決定

`RLERasterEncoder` 沒有單段長度上限（`run` 為 `uint32_t`，只在值改變時 `emit_run`），因此輸出位元組完全由「把整張緩衝以列優先順序切成最大同色段」的結果決定：同一組段、同一個順序，就產生同一串位元組與同一個檢查碼。

所以任何加速方法，只要能證明它**產生相同的最大同色段序列**，就一定逐位元組相同——不論它一次跳 1 個、8 個還是 80 個像素。第 1 步與第 2 步的 RLE 改動都以這條論證為依據，單元測試則以原演算法當對照組做差分比對（見 D10）。

段長的格式上限是 2^28 − 1（4 個位元加 3 個延伸位元組，[RasterBase.cpp:184-187](../../../third_party/prusaslicer_fork/src/libslic3r/SLA/RasterBase.cpp#L184-L187)）。機隊最大幅面為 94,197,600 像素，全黑層是單一段，仍在範圍內。超過 2^28 像素的幅面在原實作就會輸出錯誤，本設計不改變這個既有行為，只在文件與測試中註明前提。

### D2：第 1 步 RLE——64 位元字組比對加尾端零位計數

只在 `num_components == 1`（灰階，正式流程恆成立）時啟用；否則走原迴圈。

```
cur = src[0]; run = 0; p = 0
while p + 8 <= n:
    w   = load_u64(src + p)            // memcpy，不做指標轉型
    x   = w XOR (cur × 0x0101010101010101)
    if x == 0:                         // 8 個位元組都等於 cur
        run += 8; p += 8; continue
    k = ctz64(x) >> 3                  // 前 k 個位元組仍等於 cur（小端序）
    run += k; p += k
    emit(cur, run); cur = src[p]; run = 1; p += 1
while p < n:                           // 尾端不足 8 位元組，逐位元組
    ...原邏輯...
emit(cur, run)
```

- **讀取**：以 `memcpy` 載入 `uint64_t`。MSVC 與 Clang 都會把它編成單一指令，同時避開未對齊存取與 strict aliasing 的未定義行為（現行 AA 量化用的 `reinterpret_cast<uint64_t*>` 在 x86 上能動，但不在本次修改範圍）。
- **邊界**：迴圈條件 `p + 8 <= n` 保證絕不讀超過緩衝末端，不需要額外配置填充空間。
- **同色的定義**是「等於目前段的值」，因此全黑段、全白段（模型實心內部）都能一次跳 8 個。
- **`ctz64`**：以一個小的內聯函式包裝 `__builtin_ctzll`（GCC／Clang）與 `_BitScanForward64`（MSVC）。
- **位元組序**：`ctz >> 3` 的推論只在小端序成立。目前所有目標平台（x86_64、arm64）都是小端序；以編譯期判斷在大端序平台退回逐位元組路徑。
- **AA 灰邊密集時**：每次不相符都要多做一次載入、XOR 與 `ctz`，成本與原逐位元組迴圈接近，不會明顯變慢。這一點由滿版案例的 3% 門檻把關。

### D3：第 1 步預覽——改為列優先累加，零字組整段跳過

只修改整數倍快路徑 `preview_box_downscale_integer`；通用路徑不動（正式流程不會走到）。

現行迴圈順序是「目標列 → 目標欄 → 來源 n 列 → 來源 n 欄」，每處理一個目標像素就要在 n 條來源列之間跳動。新的順序改為「目標列 → 來源 n 列 → 沿著來源列連續走訪」：

```
for dy in 0..new_h:
    sums[0..new_w] = 0                       // unsigned，最大 n²×255 = 25,500
    for sy in dy*n .. dy*n+n:
        row = src + sy * w
        x = 0
        while x + 8 <= new_w * n:
            if load_u64(row + x) == 0: x += 8; continue
            for 這 8 個位元組中非零者: sums[x_i / n] += row[x_i]
            x += 8
        尾端逐位元組累加
    for dx in 0..new_w: dst[dy*new_w + dx] = sums[dx] / (n*n)
```

- **等價性**：每個目標像素累加的像素集合完全相同，整數加法可交換，最後的截斷除法也相同，因此輸出逐位元組不變。
- **走訪範圍**：只讀 `[0, new_w × n)` 欄與 `[0, new_h × n)` 列，與現行快路徑完全一致。快路徑本來就會忽略右側與底部不足一個區塊的像素（見 D7）。
- **8 位元組字組會跨越兩個目標區塊**（例如 n = 5）。這沒有關係：零字組對任何區塊的貢獻都是 0；非零字組則逐位元組歸屬到各自的 `sums[x / n]`。
- **暫存空間**：`sums` 是每次呼叫配置一次、長度 `new_w` 的陣列（16K 為 1,512 × 4 位元組），常駐 L1 快取。

### D4：第 2 步資料結構——每格 1 位元組的格子表

```
T        = 80                          // 格子邊長（像素），編譯期常數
tiles_x  = ceil(W / T)
tiles_y  = ceil(H / T)
m_tile   : std::vector<uint8_t>(tiles_x × tiles_y)   // 0 = 乾淨，1 = 寫過
m_row_any: std::vector<uint8_t>(tiles_y)             // 該格子列是否有任何一格寫過
```

**不變式 I1（乾淨即背景）**：`m_tile[ty × tiles_x + tx] == 0` ⇒ 該格內每個像素都等於背景值。
**不變式 I2（寫入必登記）**：任何像素被寫成非背景值之前，它所在的格子必須已經標為 1。允許多標（標了但沒寫），**不允許漏標**。

I1 + I2 讓緩衝**永遠是完整、正確的影像**：格子表只是「哪裡不必看」的提示。所以不讀格子表的舊使用端（PNG 編碼器、`AnycubicSLA`、`read_pixel`、GUI）完全不受影響。

**為什麼每格 1 位元組，而不是位元集合**：

| | `uint8_t` 陣列（採用） | 位元集合 |
| --- | --- | --- |
| 16K 大小 | 14,742 位元組 | 1,843 位元組 |
| 標記一段格子 | 一次 `memset` | 需處理跨字組的遮罩 |
| 讀取 | 直接索引，不需位移運算 | 需位移與遮罩 |

兩者相對於每條執行緒 94 MB 的緩衝都小到可以忽略；8 條執行緒合計約 118 KB。位元集合省下的空間沒有實際價值，卻讓標記與讀取都變複雜，因此採用位元組陣列。

**空間複雜度**：O(W × H / T²)。各機型的格子數：

| 幅面 | tiles_x × tiles_y | 格子表 | 不完整格子 |
| --- | --- | --- | --- |
| 15120 × 6230（16K） | 189 × 78 | 14,742 B | 底部一列高 70 px |
| 13320 × 5120（14K） | 167 × 64 | 10,688 B | 右側一欄寬 40 px |
| 7536 × 3240（8K） | 95 × 41 | 3,895 B | 右側寬 16 px、底部高 40 px |
| 5760 × 3600 | 72 × 45 | 3,240 B | 無 |
| 3840 × 2400／2160 | 48 × 30／27 | 1,440／1,296 B | 無 |

直式（portrait）方向時 W、H 會對調（[SL1.cpp:390-393](../../../third_party/prusaslicer_fork/src/libslic3r/Format/SL1.cpp#L390-L393)），不完整格子會換到另一個軸。因此 D7 的邊界處理必須兩軸對稱，不能假設只有底部不完整。

**為什麼 T = 80**：

- T 必須是 8 的倍數，格子邊界才會對齊 D2／D3 的 8 位元組字組。
- T 必須能被所有預覽分母 4、5、8、10 整除，也就是 40 的倍數。這樣每個預覽區塊一定完整落在同一格內（80 ÷ 10 = 8、÷ 5 = 16、÷ 4 = 20、÷ 8 = 10），不需要處理一個預覽區塊跨越兩格的情況。
- 在 40 的倍數中，40 的格子數是 80 的 4 倍（16K 為 58,968 格），每層的格子表處理量跟著變 4 倍；160 則太粗，一顆導板的邊緣就會把大片黑色格子標髒。80 是折衷的預設值，最佳值在實作後以量測決定（見 Open Questions）。

**替代方案（否決）：只記錄每列的最左、最右寫入位置。** 零件散佈在平台各處時，一列的左右界常常橫跨大半個幅面，吃不到中間的空白。前一個變更也已因同樣理由否決 bbox 級裁切。

### D5：第 2 步寫入記錄點——包一層像素格式轉接器

在 AGG 的像素格式（`agg::pixfmt_gray8`）外面包一層 `TileTrackingPixfmt<PixFmt>`，由它提供 `agg::renderer_base` 需要的方法：先依（已裁切的）座標標記格子，再轉呼叫真正的像素格式。

```
renderer_scanline_aa_solid          draw() 與 draw_binary() 共用 _draw()
        │
agg::renderer_base<TileTrackingPixfmt>    ← 在這裡完成裁切（clip box）
        │  blend_solid_hspan(x, y, len)   AA 邊緣
        │  blend_hline(x, y, len)         實心內部
        │  copy_hline(x, y, len)          clear()
        ▼
TileTrackingPixfmt  ── mark(y, x, x+len-1) ──► m_tile / m_row_any
        │
agg::pixfmt_gray8   ── 實際寫入 m_buf
```

`mark` 的計算：`ty = y / T`，`tx0 = x / T`，`tx1 = (x + len − 1) / T`，對 `m_tile[ty × tiles_x + tx0 .. tx1]` 做 `memset(1)`，並設 `m_row_any[ty] = 1`。

- **兩軌都自動涵蓋**：模型軌 `draw()` 與支撐軌 `draw_binary()` 都經由 `_draw()` → `render_scanlines` → `renderer_base`，所以兩者寫入時都會標記，不需要在呼叫端各自處理。
- **座標已經裁切**：`renderer_base` 在呼叫像素格式之前已經把跨出幅面的片段裁掉（[agg_renderer_base.h:275-297](../../../third_party/prusaslicer_fork/bundled_deps/agg/agg/agg_renderer_base.h#L275-L297)），轉接器拿到的座標一定在 `[0, W) × [0, H)` 內，不需要再檢查範圍。
- **鏡像與直式方向不影響**：路徑變換在光柵化之前就完成了，轉接器看到的是緩衝座標。
- **AA 灰邊一定被標到**：AA 邊緣的覆蓋像素本身就是 `blend_solid_hspan` 的一部分，不必另外向外擴張。
- **覆蓋率為 0 的像素也照標**：屬於多標，不違反 I2。

**只實作目前會被呼叫到的方法**（`width`、`height`、`blend_solid_hspan`、`blend_hline`、`copy_hline` 與型別別名）。C++ 樣板的成員函式只在被呼叫時才實體化，所以日後若有人在 raster 裡呼叫 `copy_bar` 之類的新寫入方法，會得到編譯錯誤，而不是一個沒有標記的靜默寫入。這與 `reset()` 設為純虛擬是同一個原則。

**替代方案（否決）：在 `_draw()` 裡自己跑掃描線迴圈，從掃描線的片段標記。** 程式較少，但片段還沒經過裁切，必須自己處理邊界；更重要的是，任何繞過 `_draw()` 的新寫入路徑都會靜默漏標。

### D6：第 2 步各消費端與執行緒重用時的重置

四個全幅面操作都改成「依格子表走訪」。它們共用同一個規則：從 `m_tile` 算出每個格子列裡「連續寫過的格子區段」，只處理這些區段，其餘直接視為背景值。**不另建快取**，每個消費端自己從格子表推導（16K 每層最多掃 14,742 位元組），避免快取失效造成的錯誤。

**① `reset()`**

```
for ty where m_row_any[ty]:
    y0 = ty × T; y1 = min(y0 + T, H)
    for 每個連續寫過的格子區段 [tx_a, tx_b]:
        x0 = tx_a × T; x1 = min((tx_b + 1) × T, W)
        for y in y0..y1: 以背景值填 m_buf[y × W + x0 .. y × W + x1)
memset(m_tile, 0); memset(m_row_any, 0)
重新套用建構時的 gamma（沿用現行行為）
```

- **直接寫入 `m_buf`，不經過轉接器**，否則清除本身會把所有格子重新標髒。
- **建構子**仍以 `clear(m_background)` 清除整張（會經過轉接器而全部標髒）；清完之後把格子表歸零。此時整張都是背景值，I1 成立。
- **執行緒重用的安全性**：格子表是 raster 實例的成員，而實例與執行緒綁定。無論工作竊取讓這條執行緒接下來處理哪一層，`reset()` 結束時 I1 對所有格子都成立，下一層與上一層是哪一層完全無關。「全部標髒」的格子表會退化成清除整張，也就是現行行為。

**② 後處理（AA 量化）**

後處理函式是 SL1 注入的 `std::function`，raster 無法得知它是否只看單一像素。因此新增一個明確的旗標：

```
struct RasterPostProcess {          // 包住現有的 RasterPostProcessor
    RasterPostProcessor fn;
    bool zero_preserving_pixel_local = false;   // 預設 false = 安全
};
```

- **旗標為 true** 表示：每個像素的輸出只取決於它自己，而且 `f(背景) == 背景`。SL1 的 AA 量化符合這兩點：`c == 0 || c == 255` 時直接返回，其餘像素各自獨立計算。SL1 只在 `blur == 0` 時設為 true。
- **為 true 時**，raster 只對寫過的區段逐列呼叫 `fn(m_buf + y × W + x0, x1 − x0, 1, 1)`。因為每個像素各自計算，把一整張拆成許多列段呼叫，結果與一次呼叫整張完全相同，SL1 的量化程式本體不必修改。乾淨格子全是 0，對它們呼叫量化也不會有任何變化，所以跳過是安全的。
- **為 false 時**（`blur > 0` 或任何未宣告的後處理），對整張緩衝呼叫一次，然後把所有格子標髒。blur 會把亮度擴散到鄰近的乾淨格子，全部標髒是最簡單且正確的做法。blur 路徑因此維持現行效能，符合 Non-Goals。
- `create_raster_grayscale_aa()` 增加一個預設為 `false` 的參數。沒有傳入的呼叫端（`AnycubicSLA`、GUI）行為不變。

**③ RLE 編碼**

在 D2 的迴圈外面加上格子走訪：

```
for y in 0..H:
    ty = y / T
    if !m_row_any[ty]:  以「W 個背景值」併入目前的同色段；continue
    for 該格子列依序每個區段 [x0, x1)（寫過與乾淨交替）:
        乾淨區段：以「x1 − x0 個背景值」併入目前的同色段
        寫過區段：對 src[y × W + x0 .. y × W + x1) 執行 D2 的字組比對
```

「併入 k 個值 v」的定義是：`v == cur` 時 `run += k`；否則先 `emit(cur, run)`，再設 `cur = v, run = k`。
**同色段會跨列延續**：`cur` 與 `run` 在換列時不重設，與原實作的列優先連續走訪一致。依 D1，最大同色段序列不變，因此輸出逐位元組相同。

**④ 預覽**

在整數倍快路徑中，條件 `T % n == 0` 成立時，每個目標像素 `(dx, dy)` 對應的來源區塊一定落在單一格子 `(dx × n / T, dy × n / T)` 內。對乾淨格子，目標值等於背景值（背景為 0 時 `dst` 已初始化為 0，直接不寫）；只有寫過的格子才執行 D3 的累加。若 `T % n != 0`（目前不會發生），退回 D3 的全幅面路徑。

**消費端介面**：不修改 `RasterEncoder` 的簽章。

- raster 新增唯讀存取 `const TileMap* written_tiles() const`（`RasterBase` 預設回傳 `nullptr`，SVG raster 不需實作）。
- `SLAArchiveWriter` 新增 `virtual SparseRasterEncoder get_sparse_encoder() const`，預設回傳空值。SL1 在 `SLA_LAYER_RLE` 開啟時回傳稀疏版 RLE 編碼器。
- `draw_layers()` 在稀疏編碼器存在且 `written_tiles()` 非空時使用稀疏版；否則照舊呼叫 `get_encoder()`。預覽同理。
- 其他格式（`AnycubicSLA`、`SL1_SVG`）不必修改。

### D7：不完整格子——所有區段右界與下界一律裁切

所有由格子換算像素範圍的地方，都使用同一組公式：

```
x0 = tx × T              x1 = min((tx + 1) × T, W)
y0 = ty × T              y1 = min((ty + 1) × T, H)
長度 = x1 − x0          （16K 最右一格 = 15120 − 15040 = 80）
高度 = y1 − y0          （16K 最下一列 = 6230 − 6160 = 70）
```

- **reset**：以裁切後的 `[x0, x1) × [y0, y1)` 填背景值，絕不寫到緩衝外。
- **RLE 的算術補正**：乾淨區段併入的背景值個數就是裁切後的 `x1 − x0`；整個格子列都乾淨時，每一列併入 `W` 個。16K 最後一個格子列有 70 列，每列併入 15,120 個背景值，所以總像素數恆為 `W × H`。
- **AA 量化**：傳給 `fn` 的長度就是裁切後的 `x1 − x0`。
- **預覽**：快路徑本來就只處理 `new_w × n` 欄與 `new_h × n` 列，目標索引額外以 `min(…, new_w)`、`min(…, new_h)` 裁切。例如 8K（n = 5）最右一格 x = 7520～7535 對應目標欄 `[1504, min(1520, 1507)) = [1504, 1507)`；來源第 7535 欄在現行快路徑中本來就不讀，稀疏版也不讀。
- **標記**：`tx1 = (x + len − 1) / T`，因為 `x + len − 1 ≤ W − 1`，結果一定小於 `tiles_x`，不需要額外裁切。

單元測試必須涵蓋：寬、高都不整除的幅面（例如 7536 × 3240 與其直式對調），以及只在最右欄、最下列、右下角單一像素寫入的情況。

### D8：保留原演算法作為對照組，並以環境變數切換

原本的逐位元組 RLE、區塊優先預覽、整張清除、整張後處理全部保留，作為參考實作：

- 環境變數 **`SLA_RASTER_FASTPATH=0`** 時，第 1 步與第 2 步都關閉，完全走參考實作。預設為開啟。沿用 `SLA_LAYER_RLE` 的既有慣例。
- 用途有三個：單元測試的差分對照組、同一支 binary 內的快速 A/B 比較、上線後出問題時不重新建置即可停用。
- **正式的「改動前」基準仍然必須由未修改的程式碼建置**。原因是參考實作與新程式碼在同一支 binary 裡，同一個重構錯誤可能同時影響兩者。

另外提供 **`SLA_RASTER_VERIFY=1`**：每層編碼後掃描整張緩衝，確認每個乾淨格子都是背景值（驗證 I1）；一旦違反就寫一行錯誤到 stderr，並讓切片以失敗結束。這個模式只在驗收與測試時開啟，不影響正式效能。

### D9：各階段計時

環境變數 **`SLA_RASTER_TIMING=1`** 時啟用。

| 計時點 | 位置 |
| --- | --- |
| `reset` | `draw_layers()` 的 `acquire()` 前後 |
| `draw_model`、`postprocess`、`draw_support` | `lvlfn` 的三段迴圈前後 |
| `encode_layer`、`encode_preview` | `draw_layers()` 的兩次 `encode()` 前後 |

- 每條執行緒以 `tbb::enumerable_thread_specific` 累加 `steady_clock` 的耗時，不在熱迴圈裡加鎖。每層只多 12 次時鐘讀取，相對於每層數十毫秒可以忽略。
- 光柵化結束時合併，寫**一行**到 stderr：`[raster-timing] {"layers":N,"threads":K,"wall_s":…,"thread_s":{"reset":…,…}}`。
- 各階段是「所有執行緒加總的秒數」，不是牆鐘時間，因此另外附上整段光柵化的牆鐘時間 `wall_s`。
- **寫到 stderr，不寫 stdout**：agent 的進度解析讀 stdout，而且 `test_slice_progress_string_contract.py` 鎖定了 stdout 的標記字串；stderr 只會被整份存成 `stderr.log`。

### D10：單元測試位置與內容

新增 `tests/sla_print/sla_raster_scan_tests.cpp`，並加入 `tests/sla_print/CMakeLists.txt`。所有測試都以參考實作（D8）當對照組，比對逐位元組結果：

- **編碼器**：全黑、全白、只有 (0,0)／(W−1,H−1) 單點、灰階雜訊、跨列延續的長同色段、段長恰為 15／16、4095／4096、1048575／1048576、緩衝長度不是 8 的倍數。
- **格子表**：不整除的幅面與其直式對調、只寫在不完整格子內、只寫在格子邊界兩側的相鄰像素、寫過後完全清空的層。
- **執行緒重用**：同一個 raster 連續處理「大面積層 → 空層 → 單點層 → 滿版層」，每層都與新建的 raster 結果相同。
- **後處理旗標**：`blur = 0` 時稀疏後處理與整張後處理相同；`blur = 1` 時所有格子被標髒，結果與參考實作相同。
- **亂數差分**：固定亂數種子產生多邊形集合，在多種幅面下比對稀疏版與參考實作。

依循既有的 `scripts/check_baseline.py` 慣例：**病患相關的 STL 不入 git**（見 [scripts/README-surg-guide-regression.md](../../../scripts/README-surg-guide-regression.md)），repo 只放工具、清單與文字形式的結果。

```
├── make_fixtures.py                      產生排版 STL、合成平板、凍結支撐

scripts/raster_bench/work/                ← gitignore（新增規則）
├── fixtures/<case>/model.stl             產生出來的排版模型
├── fixtures/<case>/support.stl           凍結的支撐網格
└── runs/<platform>-<build>-<case>-t<threads>-r<n>/

    ├── preview.sha256                    每張預覽圖的指紋
    ├── timing.json                       牆鐘、各階段、[raster-timing]、峰值 RSS
    └── meta.json                         平台、引擎 build id、fork commit、參數雜湊

└── <platform>-<timestamp>/               驗收當次的指紋清單與時間表
```

**`manifest.json` 的內容**：

- 每個案例的機型、幅面、`config.ini` 參數、執行緒數與重複次數。
- 來源模型只記**檔名與 SHA-256**，不記絕對路徑。模型目錄由 `--models` 參數或環境變數 `RASTER_BENCH_MODELS` 指定；工具不硬寫路徑（避免重蹈 `check_baseline.py` 硬寫 macOS 路徑的問題）。
- 排版以每顆的 (x, y) 位移描述。16K 為 4 × 2、8K 為 3 × 1，格距固定。
- 凍結支撐的 SHA-256。
- 合成滿版平板（200 × 110 × 2 mm）由程式碼產生，不含病患資料，可以在任何機器重現。

**凍結支撐的流程**：`make_fixtures.py --freeze-support` 只在建立基準時執行一次，以「改動前」的引擎產生 `support.stl`，並把雜湊寫回 `manifest.json`（這次提交進 git）。之後 `run_bench.py` 發現支撐檔缺少或雜湊不符時直接拒絕執行，不會自動重新產生，以免在不知情的情況下換掉比較基礎。產出的支撐檔與來源模型放在同一個內部共享位置，不入 git。

**指紋的定義**：以 Python `zipfile` 讀出 `.sl1` 與預覽 zip 中每個項目**解壓後**的位元組計算 SHA-256，按項目名稱排序，每行 `<名稱>  <sha256>`。不對 zip 檔本身取雜湊，因為 zip 標頭含時間戳記，前一個變更已經因此誤判過一次。

**比對規則**（`compare_fingerprints.py`）：

- `meta.json` 的平台標籤不同時預設拒絕比對；加 `--allow-cross-platform` 只輸出差異報告，不作為驗收依據。
- 輸出層數是否相等、第一個不同的層、不同層的總數；任一層不同時結束碼為 1。

**驗收執行矩陣**：

1. 以改動前的引擎，用 `--threads 1` 與預設執行緒數各跑一次，**先確認基準本身在不同執行緒數下一致**，否則基準不可信。
2. 以改動後的引擎，對 `--threads 1`、`2`、`8` 各跑 3 次，每一次的指紋都必須等於第 1 步的基準。
3. 時間比較只取預設執行緒數下 3 次的中位數。

**替代方案（否決）：把排版後的 STL 與支撐檔直接提交進 git。** 8 顆排版約 50 MB，repo 沒有使用 Git LFS，而且這些模型屬病患資料，違反既有慣例。

## Risks / Trade-offs

- **[漏標寫入區域 → 靜默的錯誤像素，而且可能只在特定執行緒排程下出現]** → 標記放在 AGG 的最底層寫入點，未實作的寫入方法會編譯失敗（D5）；`SLA_RASTER_VERIFY=1` 在驗收時逐層檢查 I1（D8）；以多種執行緒數與重複執行比對指紋（D11）；單元測試以參考實作做差分對照（D10）。
- **[後處理旗標被誤用：非逐像素的後處理被標成 true]** → 旗標名稱直接寫出兩個條件（逐像素、背景不變），預設為 false；SL1 只在 `blur == 0` 時設為 true；`blur = 1` 的指紋比對納入測試。
- **[滿版時標記與格子走訪的額外成本]** → 由滿版平板案例的 3% 門檻把關；若超過，先評估較大的 T，或在轉接器記住上一次標記的格子範圍以省略重複的 `memset`。
- **[AA 灰邊密集的層讓第 1 步的字組比對常常失敗]** → 最壞情況與原逐位元組迴圈相近；以標準案例的逐階段計時確認沒有退步。
- **[未定義行為與位元組序]** → 一律以 `memcpy` 載入字組；`ctz` 推論只在小端序啟用，編譯期判斷。
- **[基準漂移：支撐檔或模型被換掉]** → 雜湊記錄在 `manifest.json`，不符時拒絕執行。`model.stl` 同時綁定排版定義的雜湊，凍結支撐綁定它所屬的 `model.stl`，改了排版卻沿用舊模型或舊支撐都會被擋下。
- **[筆電量測雜訊（i7-11370H 會降頻）]** → 插電、每輪之間冷卻、取 3 次中位數並記錄最大與最小值；若最大與最小相差同時超過中位數的 5% 且絕對差值大於 0.5 秒，整組重跑。
- **[改動前後的建置環境不同]** → 兩支引擎以同一套編譯設定、在同一台機器上建置；`meta.json` 記錄 build id 與 fork commit。
- **[病患資料外流]** → STL 與支撐檔一律不入 git；evidence 只放雜湊與時間等文字。
- **[新增的虛擬函式與參數被其他格式誤用]** → 全部有安全的預設值（`nullptr`、空編碼器、`false`），不實作就等同現行行為。

## Open Questions

- **格子邊長的最佳值（已於 2.23 實測定案，2026-09-16）：T = 40**。

  量測條件：
  - 三版引擎出自同一個 `<vs_build>` 與 `Release | x64`，只有 `TileMap::T` 不同。
  - Windows 驗收機，預設執行緒數，每個案例 3 次取中位數，每次執行前閒置 60 秒。
  - **不設任何 `SLA_RASTER_*`**。`SLA_RASTER_VERIFY=1` 會逐層掃描整張畫布，成本會蓋過要量的數字（同一版引擎在開啟後主基準為 9.52 s，關閉後為 4.77 s）。正確性由 2.19 負責，這裡只量時間。
  - 每一次執行的層檔與預覽圖指紋都與 Golden 比對，全部相符：改動 T 不會改變輸出的任何一個位元組。

  | T | 主基準 16K × 8 中位數（最小～最大） | vs 基準 | 滿版 16K 平板 中位數（最小～最大） | vs 基準 | 主基準峰值 RSS |
  | ---: | --- | ---: | --- | ---: | ---: |
  | 基準 | 22.58 s（22.39～23.28） | 100.0% | 2.18 s（2.08～2.20） | 100.0% | 1441 MB |
  | **40** | **4.40 s（4.25～4.53）** | **19.5%** | **2.02 s（1.96～2.09）** | **92.4%** | **1440 MB** |
  | 80 | 4.77 s（4.67～4.89） | 21.1% | 2.08 s（2.07～2.14） | 95.3% | 1476 MB |
  | 160 | 5.65 s（5.58～5.68） | 25.0% | 2.11 s（2.01～2.21） | 96.7% | 1440 MB |

  定案理由：

  - **主基準單調偏好小格子**：19.5% → 21.1% → 25.0%，T 每加倍就慢一截。牙科導板是細長結構，格子越大，被一小段邊緣標髒卻幾乎全黑的區域就越多。T = 40 比 T = 80 快 7.8%，比 T = 160 快 22.1%。
  - **三組的離散度都不需重跑**：差距分別為 0.28 s、0.22 s、0.10 s，絕對值都遠小於 0.5 s 的門檻。三者的差異大於各自的雜訊，排序是可信的。
  - **滿版案例沒有反向代價**：T = 40 的格子表是 T = 160 的 16 倍大（16K 為 58,968 格對 3,744 格），但即使在每個格子都髒、完全跳不掉任何東西的滿版案例，T = 40 仍是三者中最快的 92.4%。格子表本身的走訪成本小到量不出來。這推翻了 D4 當初「40 的格子表處理量變 4 倍」的顧慮。
  - **峰值記憶體合規**：主基準門檻為「不高於基準」。T = 40 為 1440 MB，略低於基準的 1441 MB。T = 80 的 1476 MB（+2.4%）曾一度看似超標，但 T = 160 又回到 1440 MB，而 T = 40 的格子表比 T = 80 大 4 倍卻用得更少——可見那 35 MB 與格子表大小無關，是峰值工作集的量測抖動。選定 T = 40 之後這個疑慮不存在。
  - **T = 40 是格式允許的下限**：`T % 40 == 0` 是編譯期斷言，來自「預覽的每個 n × n 區塊（n = 4, 5, 8, 10）必須完整落在單一格子內」。再往下就會讓區塊跨格，稀疏預覽的前提失效。所以 40 不只是三者中最好，也是這個約束下能取到的最小值；趨勢雖然指向更小更好，但沒有再往下的空間。
  - 16K 幅面下 T = 40 的格子表為 378 × 156 = 58,968 格，加上 156 個列摘要，共 59,124 位元組，仍遠小於 L2 快取。

  後續影響：單元測試中依 T 推導的期望值（後處理呼叫次數、跨格拼接的同色段長度、預覽目標欄映射、格子座標）已全數改以 T = 40 重算。上方階段 0 表格中的「T=80 髒格子」欄位是當時的量測紀錄，不隨本決定改寫。
- **模型與凍結支撐的內部共享位置**：比照 `scripts/README-surg-guide-regression.md`，目前也還沒有確定的路徑，需由團隊指定後寫進 `scripts/raster_bench/README.md`。在指定之前，驗收可以在本機路徑 `D:\tool\stl\phrozen\tooth` 進行，但不寫進任何入庫檔案。
- **macOS 是否需要跑完整驗收矩陣**：proposal 只要求「每個平台各自比較改動前後」。建議 macOS 至少跑一次指紋比對（正確性），時間門檻只在 Windows 驗收機上認定；最終是否要求需另行確認。
