
- 每個案例都匯入基準線的固定支撐點清單。混合尺寸案例的清單由 `bench_steps.py` 以同樣的亂數種子產生，雜湊與基準線相同（`<case>/points.sha256`）。
- **未記錄的違規**有兩種算法，兩邊都是 0：
  - C++（`head_bridge_metrics()`）：一處接觸若被 L1、L2 或中心柱紀錄點名了它的兩個支撐頭，就算已記錄。
  - Python：把 `--threads 1` 那次 log 裡每筆紀錄的接觸座標（3 位小數）對到違規的兩個元件上，規則與 Task 4.10 相同。
  - 兩邊都把 A_prop、反向 C 輔助柱與 B 一律算成未記錄（沒有任何紀錄能點名它們）。原生過密只記錄、不列入。
- **`warnings` 檢查**逐筆核對下列項目：
  - 鍵剛好是 `code`、`head`、`route`、`contacts`，接觸點的鍵剛好是 `pos`、`with`、`dist`、`required`。
  - `code`、`route`、`with` 的值都在 spec 列舉的範圍內。
  - 警告和 log 的 `WARNING: fallback_intersection_retained` 行在順序、路徑類型、接觸數與座標上都一致。
  - 每個接觸點都落在 `heads[head]` 那個支撐頭路徑的某個元件軸線上（距離 < 1e-6 mm），這也證明 `head` 索引正確。
  - 每筆警告至少有一個接觸的 `dist < required`（`required` 為兩者半徑和）。
  - 沒有 L2 的案例完全沒有 `warnings` 鍵。
- **耗時**：每次執行前先等 CPU 連續 3 秒低於 15%（typeperf），每個案例量 5 次，取中位數。每次開始前的 CPU 負載記在 `<case>/bench.json` 的 `cpu_before`。
- **各階段對照**：用目前版本的 `analyze_tree.py`（叢集版）重算各階段 `--threads 1` 的樹。基準線、Task 3、Task 4、Task 5 的樹與 log 是當時量測留下的（本機暫存，未納入版控）。所以本表基準線的 B 與 `BASELINE.md` 不同：舊版只剪除「同一根」共用柱，把叢集成員的接觸也算成 B。

## C++ 與 Python 的一致性

`cpp_metrics.jsonl` 是 C++ 量測直接讀 builder 的結果，每個案例跑兩次（多執行緒 1 次、單執行緒 1 次），兩次的 builder 摘要相同。和 `acceptance.json`（Python）逐項比較下列 25 項，10 個案例全部相同：

- 支撐頭數、柱數、輔助柱數。
- A、A_prop、B、B（R 外）、C 柱、C 支撐頭、反向 C 輔助柱、反向 C 支撐頭（總數 / 淨 / 原生過密）。
