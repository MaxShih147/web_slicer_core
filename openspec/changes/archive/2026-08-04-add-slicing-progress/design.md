## Context

`run_slicing()` 目前以 `process.communicate()` 一次性收完切片子進程的輸出，`stderr` 落地為 `stderr.log`、`stdout` 直接丟棄。job 的對外狀態只有寫入 `status.json` 的四態（`pending` / `processing` / `completed` / `failed`），`GET /api/v2/slices/{job_id}` 亦僅回傳此四態。

但切片引擎 CLI 在 SLA 路徑早已具備進度輸出能力：其 status callback 會將 `百分比 => 階段標籤` 逐行寫入 `stdout` 並主動 flush。引擎內部對這些事件已做過整數閘門（僅在四捨五入後的百分比上升時才回報），因此整趟切片的事件量相當稀疏。

三項已驗證的上游事實構成本設計的地基：

1. **標籤保證為英文**。引擎的翻譯回呼只在 GUI 模組初始化時掛載，headless CLI 走不到該路徑，標籤巨集在回呼未掛載時原樣回傳原文。
2. **引擎回報 100% 不等於子進程完成**。回報 100% 之後，CLI 仍會寫出 `.sl1` 封存檔與 preview 封存檔，這段期間沒有任何進度事件；封存全部完成後會有一行獨立的 stdout 訊息。
3. **C stdio 與 C++ stream 的輸出順序有保證**。fork 全域未關閉 stdio 同步，故進度行（C 風格輸出）與封存完成行（C++ stream 輸出）之間的相對順序可靠，且後者會 flush。

既有的 `support-generation-error-codes` 已為本專案確立「以 stdout/stderr 文字標記為真值來源」的慣例，並明文要求不得僅保存 stderr 而丟棄 stdout。本設計延續同一慣例，不新開先例。

## Goals / Non-Goals

**Goals:**

- 讓 job 狀態 API 能對外提供切片的即時百分比與當前階段。
- 在不改動切片引擎 fork 的前提下達成上述目標。
- 完整保全 `run_slicing()` 的既有行為：`stderr.log` 落地、退出碼判定、崩潰通知、失敗狀態寫入。
- 將引擎的英文自然語言標籤隔離在後端，前端只接觸穩定識別碼。
- 讓引擎標籤的未來漂移**可被偵測**，而非默默降級。
- 以非破壞方式擴充 API，既有欄位語意與回應形狀不受影響。

**Non-Goals:**

- **不定義進度的視覺權重**。百分比如何映射到進度條、如何補間平滑、階段如何翻譯，全部屬於前端職責，本設計只負責提供忠實的原始事實。
- **不涵蓋 `run_support_generation()`**。該路徑走同一支 CLI，可於日後共用相同機制，但不在本次範圍。
- **不新增取消能力**。目前 Agent 沒有任何 cancel / terminate 端點，用戶端放棄輪詢後子進程仍會跑完，此為既有債。
- **不改動 `status.json` 的結構**。

## Decisions

### D1：消費既有 stdout，切片引擎零改動

引擎所需的進度輸出與封存完成訊號都已存在於現行 CLI 行為中，且進度行有主動 flush，管線化後即時可讀。

**替代方案：修改 fork 以輸出結構化進度（如 JSON Lines）。** 更穩固、可免除字串比對，但需重建三平台 binary（Windows / macOS / Linux），代價與本變更的效益完全不成比例。且引擎正在進行去識別化改造，額外的 fork 改動會增加該工作的合併負擔。

**取捨**：換來的是對引擎 stdout 文字內容的依賴，以 D4 的降級與告警機制承接。

### D2：雙流並行 drain，且兩流採用不同的讀取方式

改為串流讀取後，**必須以 `asyncio.gather()` 同時 drain `stdout` 與 `stderr`**，再等待進程結束。

只讀 `stdout` 會導致死鎖：切片引擎持續向 `stderr` 寫入 log，管線緩衝區填滿後子進程的寫入呼叫會阻塞，於是它不再產出 `stdout`，而父進程正在等待 `stdout` 的下一行——雙方互鎖，整趟切片永久停住。這是本變更**風險最高的單一改動點**，遠超過任何效能考量。

兩流的讀取方式必須不同：

- `stdout` — 逐行讀取。進度行極短，行導向讀取安全且直觀。
- `stderr` — **分塊讀取，不得逐行讀取**。串流讀取器對單行長度有上限，引擎的 log 可能出現超長行（例如夾帶大量幾何診斷資訊），逐行讀取會在此拋出例外而中斷整個切片。分塊讀取沒有這個限制，且 `stderr` 只需整包落地為 log，本來就不需要行語意。

**替代方案：保留 `communicate()`，改由引擎寫進度到獨立檔案。** 免除死鎖風險，但需要改 fork（違反 D1），且引入檔案輪詢的延遲與競態。

### D3：進度存放於進程內記憶體，不落地檔案

新增模組級的 job 進度字典。理由：

- Agent 以單一進程執行（伺服器啟動未指定 worker 數），切片任務以背景任務在同進程中執行，job 狀態查詢端點亦在同進程中，因此記憶體即足以貫通寫入端與讀取端。
- 事件量本來就稀疏（引擎內部已有整數閘門），**不需要任何 throttle 或 debounce**——加了反而引入延遲與額外狀態機。

**為何不寫進 `status.json`：** `write_job_status()` 是整包覆寫固定結構，`run_slicing()` 在頭尾各呼叫一次；進度若共用同檔就變成 read-modify-write，且會與結尾的終態覆寫互相踩踏。更嚴重的是 `read_job_status()` 的 JSON 解析沒有例外防護，讀到半寫入的檔案會讓狀態查詢直接 500，使輪詢中的用戶端整個失敗。此競態已潛伏於既有的 ortho 進度實作中，本設計不複製該模式。

**替代方案：獨立的 `progress.json` + 原子換檔。** 可跨進程、留下除錯痕跡，但在單進程前提下純屬多餘的 IO 與複雜度。若日後 Agent 改為多 worker，此為既定的升級路徑。

**生命週期**：job 進入終態時清除，清除動作置於 `finally` 以涵蓋例外路徑。**清除必須發生在終態寫入 `status.json` 之後**——反序會出現「狀態仍為 processing、但進度憑空消失」的空窗，讓用戶端看到進度倒退。對應地，`progress` 欄位缺席必須被定義為「本次無更新」而非「進度為 0」，此語意需寫入 API 契約。

### D4：階段標籤映射為 Enum，採正規化精確比對

後端將引擎標籤映射為穩定的 `STAGE_*` 識別碼後才對外提供。前端因而只依賴本變更定義的 Enum 集合，不接觸引擎字串。

**比對方式採正規化後精確比對**（統一大小寫、去除尾端標點、收斂空白），**不使用子字串比對**。引擎的標籤中有三個共享同一前綴（分別對應「切片模型」「切片支撐」「切片完成」三種語意完全不同的階段），子字串比對必然誤判。另有一個標籤帶有尾端句點，正規化步驟正是為了吸收這類不一致。

**未識別時降級為通用切片階段，並記錄一次告警。** 告警不可省略——引擎正在進行去識別化改造，字串調整是可預期的；若無告警，映射漂移會讓所有階段默默退化成通用值，而沒有任何人會發現。這一行 log 是這條字串耦合**唯一的可觀測性手段**。

### D5：後端回報原始引擎百分比，權重分配留給前端

進度事件對外提供的是**引擎自報的原始百分比（0–100）加上階段識別碼**，後端不做任何縮放或加權。

這是本設計的核心分層原則：後端陳述事實，前端決定呈現。前端的進度條還需要涵蓋切片完成後的封裝與儲存階段，其權重分配是前端的產品決策，若讓後端預先縮放，這個決策就會被錯誤地固定在錯誤的層級，日後調整需要動兩個 repo。

**由此推導出封存尾段的處理方式**：引擎回報 100% 與子進程真正結束是兩個不同的時間點（見 Context 第 2 點），中間隔著封存寫檔。後端**不以百分比區分這兩者**（兩者都是 100），而是**以階段識別碼區分**：

- 引擎自報 100% → 標記為「收尾中」階段
- 封存完成訊號出現 → 標記為「封存完成」階段

前端據此得知「引擎算完了但還在寫檔」與「檔案已寫完」的差別，並自行決定兩者對應的進度條位置。封存完成訊號同樣來自 stdout，且是 fork 自有的程式碼（非上游），字串漂移風險低於引擎內建的標籤。

**替代方案：後端直接回報加權後的百分比。** 前端更省事，但把產品決策下沉到錯誤的層級，且使後端與特定前端的 UI 佈局綁定。

### D6：`progress` 為可選欄位，非破壞性擴充

`GET /api/v2/slices/{job_id}` 的回應在進度可用時附上 `progress` 物件（百分比 + 階段識別碼），不可用時**整個欄位省略**，不得填入 0 或 null 佔位——前者會讓用戶端誤判為進度倒退，後者迫使用戶端處理兩種「無進度」表示法。

既有欄位一律不動。未帶進度的 job（含尚未執行的 pending 分支、以及舊版行為）回應形狀與現況完全一致，用戶端可漸進採用。

### D7：後端亦施加單調保護

百分比在寫入進度字典前取與前值的最大值。引擎的多物件迴圈理論上已保證單調，但此保護成本為零，且能防止解析誤判或未來引擎行為變動直接外流成用戶端可見的進度倒退。

### D8：應用層須設定 `agent` 套件的 logging

真機驗證時發現 `agent/main.py` 完全沒有 logging 設定，而 uvicorn 只設定自己的 logger。結果是 `agent.*` 的所有訊息在實機上被丟棄——**D4 的標籤漂移告警與封存尾段的耗時量測都形同無效**，兩者恰好是本設計僅有的兩個執行期可觀測性手段。

修正落在 `agent/main.py`（應用進入點，而非各模組——設定 logging 是應用的職責）：只為 `agent` 套件 logger 掛上 handler 並設為 INFO，**不動 root logger**，否則會連帶打開第三方套件（PIL、trimesh 等）的 INFO 噪音。以 handler 存在與否保持冪等，`--reload` 重複匯入不會疊加 handler。

**替代方案：`logging.basicConfig()`。** 一行就好，但會開啟全域 INFO，把第三方雜訊灌進 Agent 主控台，反而更難發現本設計真正在意的那兩則訊息。

## Risks / Trade-offs

**[管線死鎖]** 只 drain 單一串流會讓切片永久卡住，且症狀是「無錯誤、無輸出、無限等待」，極難從現場診斷。
→ 以 D2 的雙流並行 drain 消除。此為必要條件而非最佳化，需納入驗收：以會大量寫入 `stderr` 的情境跑完整趟切片，確認不卡死。

**[超長 log 行導致例外]** `stderr` 若逐行讀取，遇到超過串流行長上限的單行會拋出例外，使原本能成功的切片轉為失敗。
→ `stderr` 一律分塊讀取（D2）。此風險隱蔽且非決定性（取決於模型內容），不能靠測試碰運氣發現，必須在設計層直接排除。

**[引擎標籤漂移]** 去識別化改造可能調整標籤字串，導致映射失效。
→ 未識別即降級為通用階段（功能不中斷、進度百分比仍正確），並記錄告警使漂移可被發現（D4）。**這是刻意接受的耦合**：換取零 fork 改動與零 binary 重建。

**[進度字典記憶體殘留]** job 若在非預期路徑結束而未清除，字典會持續累積。
→ 清除置於 `finally`；且每筆項目極小、Agent 為使用者本機單人服務，實務上界有限。

**[進度與終態的競態]** 進度字典與 `status.json` 是兩個獨立來源，兩者的更新不具原子性。
→ 以固定順序（先寫終態、後清進度）收斂為單一無害方向，並在 API 契約中定義「欄位缺席 = 無更新」，使用戶端的單調保護足以承接（D3）。

**[封存尾段時長未知]** 引擎回報 100% 到子進程結束之間的實際耗時目前沒有任何量測數據，前端無從合理分配這段的進度條寬度。
→ 在本變更中加入一行零成本的量測記錄（自「引擎自報完成」到「子進程結束」的時間差），供前端日後校準。這是刻意保留的已知未知，不阻塞交付。

**[用戶端放棄後子進程續跑]** 前端改用停滯判定放棄輪詢後，切片子進程仍會跑完並佔用 CPU。
→ 既有債，非本變更引入（現行的固定超時同樣如此）。取消能力需要新的端點與進程控管，另案處理。

## Migration Plan

無資料遷移、無結構變更、無破壞性調整。

- **部署**：隨 Agent 版本更新即可生效。舊版前端不讀取 `progress` 欄位，行為完全不變。
- **相容性**：新版前端遇到未更新的 Agent 時收不到 `progress` 欄位，應退回不定態顯示——此為前端變更需承接的降級路徑。
- **回滾**：還原 `run_slicing()` 的子進程執行方式即可，無殘留狀態需清理（進度僅存於記憶體，進程重啟即消失）。

## Open Questions

### 已解決

**封存尾段的實際耗時分布** — 已於真機量測（Windows / 繁中 cp950 環境，2026-08-04）：

| 情境 | 模型 | 層數 | 全程 | 封存尾段（FINALIZING→ARCHIVED） |
|---|---|---|---|---|
| 小模型 | 5.4 MB | 466 | 4.0s | **0.11s** |
| 大型牙科盤（匯入支撐） | 46 MB + 84 MB 支撐 | 632 | 30.5s | **0.45s** |

**結論與原假設相反：封存尾段極短**（次秒級），並非設計時擔心的十數秒。前端為它保留的 76→80 這 4 個進度條點過於慷慨，校準時可上調至 78–79。

同一批量測順帶取得兩個更重要的數字，前端配置補間參數時應以它們為準：

- **首個進度事件前的靜默 6.93s**（大型 STL 載入期間 `progress` 欄位不存在）——這是實際上最長的無資訊區間，發生在進度條起點。
- **最長中段停滯 9.03s**（55% `STAGE_SLICING_SUPPORTS`）——仍在前端 pseudo-progress 的可見移動預算內。
- **最大瞬時跳躍 0→27%（0.12s）**——前端的 catch-up 速度上限正是為此而設。

**切片子進程是否需要沿用語系鎖定**（`sla_operations._english_locale_env()`）— **不需要，維持現狀不改動**。

兩項證據：結構上，`_u8L` 走的 `I18N::translate()` 在回呼未掛載時原樣回傳，而全 repo 唯一呼叫 `set_translate_callback` 的是 GUI 模組，headless CLI 走不到；實測上，在 `Chinese (Traditional)_Taiwan / cp950` 環境下的兩趟真實切片映射出 9 個相異且正確的階段識別碼——若語系有影響，它們會全部降級為 `STAGE_SLICING`。

為此變動切片子進程的環境變數只會帶來風險（可能牽動數值格式化）而無收益。

### 待評估


- **`run_support_generation()` 是否共用同一機制**。該路徑同樣執行 CLI 且同樣丟棄進度，機制可完整重用；是否納入取決於支撐預覽的實際等待時間是否構成體驗問題，待前端回饋後再評估。
