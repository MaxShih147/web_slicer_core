Crash & OS diagnostics

03 · Crash & diagnostics OS 可讀堆疊去品牌＋崩潰診斷表面總表
白話說明

這在做什麼？程式萬一當掉，作業系統（Windows／Mac）會自動生成一份「當機報告」，裡面記錄是哪個程式、哪一段出錯。客服、送修單位、甚至第三方都可能看到這份報告。以前報告裡會冒出 Prusa／slic3r 的字樣；現在連這些藏在技術細節裡的名字也一併清乾淨。做法之一是 strip——把編譯時附帶的「除錯名冊（符號表）」從程式檔中移除：功能完全不變，但外部工具再也讀不到原始函式名稱。

會影響功能嗎？不會。程式該怎麼跑還是怎麼跑，只是「當掉時報告上寫的名字」換成中性名稱。

為什麼重要？當機報告是最不容易注意、卻最容易洩漏來源的地方。這是最深、最技術性的一層；連這裡都清掉，代表從一般使用者到工程師層級都查不出原始品牌。

08 · Naming rules 名稱怎麼來的、為什麼合規
白話說明

這在做什麼？把「換什麼名字」講清楚：不是隨手取的，而是先決定要表達的功能角色（這是切片引擎、這是核心模組、這是背景執行緒），再按照每種東西各自的技術規則（能用什麼字元、最長幾個字）轉成正式名稱。

會影響功能嗎？不會。這一節只解釋命名的依據與可追溯性，不動任何程式邏輯。

為什麼重要？當有人問「這些名字怎麼來的、有沒有依據」，可以直接指出：每個決策都對應一條業界規範或作業系統限制，可稽核、可重現，而不是換一個新品牌。

技術細節（各載體的字元與長度規則）
載體合法字元／格式長度上限為何這樣選
可執行檔名小寫字母、數字、連字號（kebab-case）檔名系統上限（實務遠小於）命令列輸入友善；符合 POSIX 可攜檔名字集與 CLI 工具慣例（如 clang-format、docker-compose）
DLL 基底名字母、數字、底線（snake_case）路徑長度上限模組名貼近識別字語意；避免連字號在匯入庫／建置腳本被誤解析
C 匯出符號[A-Za-z_] 開頭，其後 [A-Za-z0-9_]*連結器限制語言規定：識別字不允許連字號 → 必用底線；extern "C" 讓名稱不被 C++ mangling，供 GetProcAddress 穩定解析
Thread 名中性描述（kebab-case）15 字元（含 NUL 共 16 byte）Linux pthread_setname_np 硬上限 16 byte 最嚴；取 ≤15 讓 Linux／macOS／Windows 同名可設，跨平台一致
版本字串MAJOR.MINOR.PATCH＋+build—採 SemVer 2.0.0；build metadata 放 + 後段，不影響版本先後比較
身分欄位自由字串（去品牌）—Win VERSIONINFO 與 Authenticode 主體一致；mac headless CLI 用中性 codesign identifier，不套用 .app 的 reverse-DNS Bundle ID
一句話：每個名稱＝「功能角色詞」依「該載體的字元／長度規範」生成，條條可對回外部標準或 OS 限制。
