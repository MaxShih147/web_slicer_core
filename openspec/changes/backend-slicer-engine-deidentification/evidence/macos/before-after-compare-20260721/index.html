02b · Get Info 檔案大小 為什麼去識別化前後大小不一樣？
牙科週會備註

現象：Finder「顯示簡介」可見 macOS 引擎執行檔前後大小不同（實測約 88.3 MB → 58.9 MB，約小 30 MB／約 −30%）。作用對象是單一 Mach-O：slicer-engine（舊名 PrusaSlicer），不是整個 Launcher.app／DMG。

主要原因：為了去識別化，建置／打包時對同一支執行檔做了兩件事（拿掉的是「函式名對照資料」，不是切片功能）：

  1. 編譯時收斂對外可見符號（約 −6～−10 MB）
    只保留程式啟動必要的入口（_main），其他函式名不對外公開（-fvisibility=hidden ＋ -Wl,-exported_symbol,_main）。
  2. 打包時移除執行檔中的符號表（strip）（約 −19 MB）
    把編譯後附帶的「函式名對照表」從出貨檔刪掉；完整符號改封存在內部 .dSYM，不隨正式包出貨。

背景補充：大型 C++ 程式（大量 template：Eigen／boost／cereal／libslic3r）編譯後會附帶一份很長的「函式名對照表」（符號表），方便除錯與看 crash 堆疊；這份表本身就很大，原本就存放在同一個執行檔內部（Mach-O __LINKEDIT），不是少包了別的套件。

會影響功能嗎？不會。不改演算法、不刪執行碼；CLI／切片照常跑。改變的是可觀測表面：對外 crash 只剩位址（imageOffset），看不到品牌／函式名——這正是去識別 L2 目標。內部除錯用匹配的私有 .dSYM 即可還原。

易混淆點：這組 Get Info 對照的兩邊都是 headless CLI（本來就沒編進 wxWidgets／GUI）；大小差來自符號收斂＋strip，不是「AFTER 少包了 GUI」。

一句話：變小 ≠ 功能變少；是把除錯用的函式名冊移出正式包（約 88 MB → 約 59 MB）。

白話說明

這在做什麼？程式萬一當掉，Mac 會自動在「主控台（Console）」與 DiagnosticReports 產生一份 .ips 當機報告，裡面記錄是哪個程式、哪一段出錯。客服、送修單位、甚至第三方都可能看到。以前報告裡會冒出 Slic3r::／Prusa 的字樣；現在連這些藏在技術細節裡的名字也一併清乾淨。做法之一是 strip——把編譯時附帶的「除錯名冊（符號表）」從程式檔中移除：功能完全不變，但外部工具再也讀不到原始函式名稱。

08 · Naming rules 名稱怎麼來的、為什麼合規
白話說明

這在做什麼？把「換什麼名字」講清楚：不是隨手取的，而是先決定要表達的功能角色（這是切片引擎、這是核心模組、這是背景執行緒），再按照每種東西各自的技術規則（能用什麼字元、最長幾個字）轉成正式名稱。

會影響功能嗎？不會。這一節只解釋命名的依據與可追溯性，不動任何程式邏輯。

為什麼重要？當有人問「這些名字怎麼來的、有沒有依據」，可以直接指出：每個決策都對應一條業界規範或作業系統限制，可稽核、可重現，而不是換一個新品牌。

技術細節（各載體的字元與長度規則）
載體合法字元／格式長度上限為何這樣選
可執行檔名小寫字母、數字、連字號（kebab-case）檔名系統上限（實務遠小於）命令列輸入友善；符合 POSIX 可攜檔名字集與 CLI 工具慣例（如 clang-format、docker-compose）
DLL 基底名字母、數字、底線（snake_case）路徑長度上限模組名貼近識別字語意；避免連字號在匯入庫／建置腳本被誤解析
C 匯出符號[A-Za-z_] 開頭，其後 [A-Za-z0-9_]*連結器限制語言規定：識別字不允許連字號 → 必用底線；extern "C" 讓名稱不被 C++ mangling，供 GetProcAddress 穩定解析
Thread 名中性描述（kebab-case）15 字元（含 NUL 共 16 byte）Linux pthread_setname_np 硬上限 16 byte 最嚴；取 ≤15 讓 Linux／macOS／Windows 同名可設，跨平台一致
版本字串MAJOR.MINOR.PATCH＋+build—採 SemVer 2.0.0；build metadata 放 + 後段，不影響版本先後比較
身分欄位自由字串（去品牌）—Win VERSIONINFO 與 Authenticode 主體一致；mac headless CLI 用中性 codesign identifier，不套用 .app 的 reverse-DNS Bundle ID
一句話：每個名稱＝「功能角色詞」依「該載體的字元／長度規範」生成，條條可對回外部標準或 OS 限制。
